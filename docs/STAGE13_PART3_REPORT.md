# Отчёт по Этапу 13, часть 3 — авторизация, политики и аудит

## Результат

Подготовлена производственная серверная модель принятия решений о доступе: RBAC, permission-based access и object-level ownership объединены единым policy layer. Добавлены append-only аудит и типизированная система security events.

Новая инфраструктура не подключена к Landing, onboarding, Dashboard, Admin или другим страницам. Пользовательские маршруты и frontend не изменялись.

## Что реализовано

### RBAC foundation

Создана единая модель серверных политик, которая поддерживает:

- обязательную аутентификацию;
- наличие хотя бы одной разрешённой роли;
- наличие всех требуемых permissions;
- проверку владельца объекта;
- композицию правил через `all` и `any`.

Решение принимается только по `AuthenticatedPrincipal`, сформированному сервером из актуальных связей `User → Role → Permission` в базе. Клиентские роли, permissions и признаки владельца не являются источником истины.

Политики работают по принципу deny-by-default. Пустое, некорректное или несовпавшее правило не разрешает доступ.

### Permission evaluation service

`PermissionEvaluationService` стал единой точкой проверки:

- роли;
- permissions;
- ownership;
- составных политик.

Сервис возвращает типизированное решение с ключом политики и нейтральной причиной отказа. Он не содержит бизнес-ролей и не зависит от Dashboard, Admin, API или Server Actions.

### Object-level authorization

Добавлен общий контракт `OwnershipResolver`. Он получает ссылку на будущую сущность и текущего серверного principal, после чего возвращает объект авторизации с:

- типом;
- идентификатором;
- серверно установленным `ownerId`.

Authorization middleware принимает отдельный server-side loader ресурса. Таким образом, будущий API не должен доверять `ownerId`, переданному браузером. Если ресурс или владелец отсутствует либо не совпадает, доступ запрещается.

Бизнес-модели и object resolvers для них не создавались.

### Authorization guards и middleware

Подготовлены:

- универсальный guard для server actions и серверных сервисов;
- middleware для Fetch API / route handlers;
- типизированный контекст с подтверждённым principal и серверным ресурсом;
- ответы `401` для отсутствующей аутентификации;
- ответы `403` для отклонённой политики.

Middleware не подключён к существующим маршрутам. Реальные API не создавались.

### Server policy layer

Политики вынесены в самостоятельный `lib/policies`. Будущая бизнес-логика должна запрашивать решение у policy layer, а не проверять роли вручную внутри компонентов, endpoints или сервисов.

Ключи политик, ролей и permissions валидируются. Никакие инфраструктурные или продуктовые роли не засеяны и не зашиты в код.

### Append-only audit foundation

Добавлена инфраструктурная модель `AuditEvent`:

- actor type;
- actor id;
- внутренний session id без bearer-токена;
- action;
- target type и target id;
- server timestamp;
- структурированная metadata.

Неизменяемость обеспечивается двумя уровнями:

1. Repository предоставляет только операцию `append` и не имеет `update` или `delete`.
2. PostgreSQL-миграция создаёт trigger, запрещающий `UPDATE` и `DELETE` таблицы аудита.

Actor хранится как снимок идентификатора без внешнего ключа. Поэтому последующее удаление или изменение пользователя не переписывает историческое событие.

### Защита audit metadata

Перед записью metadata проходит серверную нормализацию:

- запрещены ключи с паролями, токенами, cookies, authorization, секретами и URL базы;
- ограничены глубина, количество полей, размер массивов, строк и общего JSON;
- запрещены неподдерживаемые объекты и нечисловые значения;
- управляющие переносы строк удаляются для защиты последующей обработки журналов.

В audit event не записываются bearer session token, password hash или секрет окружения.

### Типизированные security events

Подготовлены события:

- успешный login;
- неуспешный login;
- logout;
- refresh сессии;
- отзыв сессии;
- отказ authorization policy.

Для каждого типа определена собственная metadata: метод входа, безопасная причина, scope выхода, факт ротации, причина отзыва или ключ отклонённой политики. `SecurityEventService` преобразует событие в append-only audit event.

Security events не подключены к существующему auth flow и не создают записи без явного будущего вызова.

### Prisma и миграции

В Prisma добавлена только инфраструктурная сущность `AuditEvent` и индексы для поиска по:

- actor и времени;
- action и времени;
- target;
- общей временной последовательности.

Создана отдельная миграция append-only аудита. Она не применялась к реальной базе.

## Архитектурные решения

1. **Deny by default.** Доступ разрешается только при явном успешном результате политики.
2. **Центральный evaluator.** Role, permission и ownership не проверяются разрозненными условными выражениями.
3. **Композиционные политики.** `all` и `any` позволяют расширять правила без переноса проверок в бизнес-код.
4. **Server-resolved ownership.** Владелец будущей сущности должен загружаться серверным repository или resolver.
5. **Свежие серверные permissions.** Auth repository получает роли и permissions из базы при проверке сессии; клиентское состояние не участвует.
6. **Append-only audit.** Неизменяемость закреплена контрактом приложения и ограничением PostgreSQL.
7. **Разделение audit и logger.** Операционный logger не заменяет долгосрочный журнал действий и security events.
8. **Минимизация данных.** Audit metadata ограничена и не принимает аутентификационные секреты.
9. **Независимость от delivery layer.** Одинаковые policy и guards пригодны для Dashboard, Admin, API и Server Actions.

## Что остаётся до завершения Этапа 13

- назначение владельцев инфраструктуры и безопасности;
- проектирование и утверждение реальных инфраструктурных ролей и permissions;
- подключение guards к конкретным защищённым операциям отдельным этапом;
- endpoints и server actions аутентификации;
- object-level resolvers для будущих доменных сущностей;
- интеграция security events в login, logout, refresh и denied decisions;
- защита от brute force и rate limiting;
- восстановление доступа, MFA и управление устройствами;
- объектный и полевой контроль чувствительных данных;
- шифрование применимых данных и защита вложений;

- регламенты инцидентов, утечек, экспорта и удаления персональных данных.
