# Доменная модель VX House

## Статус документа

Документ фиксирует серверные доменные границы и контракты данных, подготовленные в Stage 13 — Part 5. Продуктовые правила определяются `PRODUCT_V2.md`, экономика — `ECONOMY.md`, порядок реализации — `ROADMAP.md`.

Модель пока не подключена к интерфейсу, API или Server Actions. Она не означает, что пользовательские данные, начисления, задания, выплаты или поддержка уже работают.

## 1. Базовые правила

- Сервер является единственным источником истины для роли, рынка, владения сущностью и прав доступа.
- Игрок и партнёр — продуктовые роли профиля. Они не заменяют инфраструктурные роли и permissions сотрудников.
- Турция и Азербайджан моделируются как явные рынки `TR` и `AZ`, а не как строки из клиента.
- VX Points, ранг, Trust Score и VX Rewards хранятся раздельно.
- Денежное значение существует только у VX Reward и всегда сопровождается валютой.
- Версии опубликованных условий не перезаписываются.
- Критическая история и экономические журналы добавляются новыми событиями.
- Повторная обработка команды не должна создавать второй результат: для этого используются idempotency key и уникальные ограничения.
- В модели отсутствуют ставки, депозиты, игровой баланс и казино-сущности.
- Не собираются дата рождения, документы личности, платёжные реквизиты и другие лишние персональные данные. Их добавление возможно только после отдельного решения о необходимости, законности и защите.

## 2. Доменные границы

| Граница | Владеет | Назначение |
|---|---|---|
| Identity and Profile | `UserProfile`, `PlayerProfile`, `PartnerProfile` | Продуктовая роль, рынок, язык, контакт и состояние доступа |
| Market and Localization | `Market`, `MarketCode`, `LanguageCode` | Стартовые рынки и языковая настройка без реализации локализации |
| Consent | `ConsentDocument`, `ConsentVersion`, `UserConsent` | Версионированные правила, приватность, 18+ и факт принятия |
| Partner Services | `PartnerService`, `PartnerServiceMarket`, `Promocode` | Реестр сервисов, доступность по рынку и защищённые коды |
| Opportunities | `Opportunity`, `OpportunityAudience`, `OpportunityEligibility` | Витрина и объяснимая доступность для конкретного пользователя |
| Instructions | `Instruction`, `InstructionVersion`, `InstructionStep`, `InstructionAudience` | Управляемый и версионированный пошаговый контент |
| Tasks and Submissions | `TaskDefinition`, `TaskVersion`, `UserTask`, `TaskSubmission`, `SubmissionVersion`, `SubmissionReview` | Полный проверяемый цикл задания без уничтожения прошлых условий и отправок |
| VX Points | `VXPointsLedgerEntry` | Неизменяемый журнал внутреннего прогресса |
| Ranks | `RankDefinition`, `UserRank` | Версии критериев пяти рангов и история присвоений |
| Trust Score | `TrustScoreEvent`, `TrustScoreSnapshot` | Объяснимые события доверия и производный текущий снимок |

| Support and Appeals | `SupportConversation`, `SupportMessage`, `SupportInternalNote`, `SupportStatusHistory`, `Appeal` | Диалог, внутренний контекст и пересмотр спорного решения |
| Forecasts and Content | `Forecast`, `ForecastVersion`, `ForecastAccessRule` | Версионированные аналитические материалы и серверные правила доступа |

| Admin Operations | Связи менеджера, проверяющего, автора, оператора и approver | Управляющие действия без отдельной копии продуктовых сущностей |
| Audit and Security | `Role`, `Permission`, `AuditEvent`, политики доступа | Инфраструктурные права, неизменяемый аудит и безопасность |

Это логические модули внутри одного приложения. Они не являются микросервисами.

## 3. Identity, профиль и рынки

`User` остаётся инфраструктурной идентичностью для входа и сессий. `UserProfile` содержит только продуктовые атрибуты:

- продуктовую роль `PLAYER` или `PARTNER`;
- рынок `TR` или `AZ` через relation к `Market`;
- предпочтительный язык `RU`, `TR` или `AZ`;
- состояние подтверждения контакта;
- состояние аккаунта и объяснимую причину ограничения.

`PlayerProfile` и `PartnerProfile` отделяют ролевой статус от общей идентичности. Партнёрский профиль поддерживает ручное одобрение с автором и временем. Клиент не может назначить себе роль или рынок.

## 4. Согласия

`ConsentDocument` определяет вид согласия. Каждая редакция хранится в `ConsentVersion` с номером, языком, hash содержимого и периодом действия. `UserConsent` связывает пользователя с конкретной версией и временем принятия.

18+, правила использования и политика конфиденциальности должны быть отдельными документами или явно разделёнными версиями. Новый текст не изменяет прошлый факт согласия.

## 5. Партнёрские сервисы и возможности

`PartnerService` — подтверждённый реестр внешнего сервиса. `PartnerServiceMarket` задаёт отдельную доступность и версию условий для каждого рынка.

`Opportunity` — витринная сущность. Она может вести к заданию, инструкции, промокоду, прогнозу или персональному условию. `OpportunityAudience` задаёт разрешённую комбинацию роли и рынка. `OpportunityEligibility` сохраняет результат серверной проверки для пользователя, причину, объяснение, версию политики и idempotency key.

Историческая оценка доступности не перезаписывается. Актуальность определяется временем и политикой сервиса.

## 6. Инструкции и версии

`Instruction` является стабильным агрегатом. Содержимое хранится в `InstructionVersion`:

- номер версии и язык;
- публикационный статус;
- hash содержимого;
- автор и время публикации;
- ссылка на предыдущую версию;
- аудитория по роли и рынку.

Шаги хранятся в `InstructionStep` с уникальной позицией внутри версии. Принятое задание ссылается на конкретную версию инструкции, поэтому последующая редакция не меняет уже принятые условия.

## 7. Задания, отправки и решения

`TaskDefinition` — стабильная сущность задания. `TaskVersion` фиксирует опубликованные условия, ограничения, формат результата, правило повторной отправки, возможный Reward, правило Points, сроки, hash условий и применимую инструкцию.

`UserTask` связывает пользователя с конкретной версией задания и номером попытки. База проверяет, что выбранная версия принадлежит тому же заданию. `assignmentKey` защищает назначение от повторной обработки.

`TaskSubmission` объединяет повторные отправки, а каждая `SubmissionVersion` сохраняется отдельно. Новая отправка не заменяет старую. `SubmissionReview` хранит решение по конкретной версии результата, проверяющего, причину, комментарий и время. Решение проверки является append-only.

`UserTaskStatusHistory` сохраняет все изменения пользовательского состояния задания. Текущее поле `UserTask.status` является рабочим снимком, а история — источником объяснения.

## 8. Экономика

### VX Points

`VXPointsLedgerEntry` — append-only ledger. Запись содержит изменение, состояние, источник, причину, версию правила и уникальный idempotency key. Отмена создаёт отдельную обратную запись и ссылается на исходную.

VX Points не расходуются как валюта и не имеют currency.

### Ранги

`RankDefinition` хранит конфигурируемую версию критериев и преимуществ для рангов `EXPLORER`, `NAVIGATOR`, `ATLAS`, `PRIME`, `SIGNATURE`. Scope может учитывать роль и рынок.

`UserRank` — append-only история присвоений. Она содержит причину, применимую версию определения, предыдущую запись и idempotency key. Текущий ранг определяется последним допустимым событием, а не редактированием прошлой записи.

### Trust Score

`TrustScoreEvent` содержит delta, значения до и после, источник, причину, версию правила, возможность апелляции и idempotency key. База ограничивает значения диапазоном 0–100 и проверяет арифметическую связь.

`TrustScoreSnapshot` — производная оптимизация чтения. Источником объяснения остаются события; снимок можно восстановить из них.

### VX Rewards

`RewardType` определяет денежный или неденежный вид. `VXReward` содержит основание, значение, статус и сроки. Денежное значение хранится как decimal и трёхбуквенный код валюты. Неденежное значение хранится отдельно и не суммируется с деньгами.

`RewardStatusHistory` является append-only. Повторное создание Reward по одному основанию блокирует idempotency key.

## 9. Поддержка и апелляции

`SupportConversation` хранит разрешённый контекст, категорию, приоритет, состояние и назначенного оператора. Сообщения пользователя и оператора находятся в `SupportMessage`; внутренние заметки — в отдельной `SupportInternalNote` и не входят в пользовательский контракт.

Текущий статус диалога дополняется неизменяемым `SupportStatusHistory`.

`Appeal` относится минимум к одному спорному решению: проверке отправки, событию Trust Score или Reward. Апелляция может быть связана с диалогом поддержки и имеет отдельного проверяющего, решение и время.

## 10. Прогнозы, промокоды и уведомления

`ForecastVersion` хранит автора через агрегат `Forecast`, язык, обязательное предупреждение, период актуальности, версию и статус публикации. `ForecastAccessRule` задаёт роль, рынок, минимальный ранг и при необходимости конкретного пользователя.

`Promocode` хранит код только как защищённый payload и fingerprint. Открытые поля описывают сервис, рынок, роль, срок и инструкцию.

`Notification` содержит полезное событие, канал, статус, связанный объект и idempotency key. Клиентские уведомления не являются источником продуктового состояния.

## 11. Ownership и права

- Владелец профиля, задания пользователя, Reward, обращения и уведомления определяется по server-side relation к `User`.
- Сотрудники связаны с сущностями как менеджер задания, проверяющий, автор прогноза, оператор, автор внутренней заметки или reviewer апелляции.
- Проверка ownership выполняется общей policy layer из Stage 13 — Part 3.
- Actor id в неизменяемой истории сохраняется как исторический снимок там, где удаление аккаунта сотрудника не должно разрушать аудит.
- Product role не используется вместо инфраструктурных permissions.

## 12. Жизненные циклы

Переходы централизованы в `lib/domain/status-machine.ts` и запрещены по умолчанию.

| Сущность | Основной путь |
|---|---|
| Account | `PENDING → ACTIVE → SUSPENDED/CLOSED`; возврат возможен только из `SUSPENDED` |
| Publication | `DRAFT → IN_REVIEW → PUBLISHED → HIDDEN/ARCHIVED` |
| User task | `AVAILABLE → ACCEPTED → IN_PROGRESS → AWAITING_SUBMISSION → SUBMITTED → UNDER_REVIEW → решение` |
| Submission | `DRAFT → SUBMITTED` или `WITHDRAWN` |
| Review | `PENDING → UNDER_REVIEW → CLARIFICATION/RESUBMISSION/CONFIRMED/REJECTED` |
| Reward | `EXPECTED → AWAITING_CONFIRMATION → CONFIRMED → PREPARING/AVAILABLE → PROVIDED` с объяснимыми ветками отказа, отмены и истечения |
| Support | `CREATED → ASSIGNED → WAITING_OPERATOR/WAITING_USER → RESOLVED → CLOSED` с контролируемым возобновлением |
| Appeal | `DRAFT → SUBMITTED → UNDER_REVIEW → UPHELD/PARTIALLY_UPHELD/DENIED` |
| Forecast | `DRAFT → IN_REVIEW → PUBLISHED → SUPERSEDED/RETRACTED/ARCHIVED` |

Любой переход вне таблицы отклоняется. Смена текущего состояния должна одновременно создавать запись соответствующей истории в одной транзакции после реализации сервисов.

## 13. Версионирование и неизменяемость

Уникальные версии установлены для:

- согласий: документ + версия + язык;
- инструкций: инструкция + версия + язык;
- заданий: определение + версия;
- отправок: отправка + версия;
- прогнозов: прогноз + версия + язык;
- рангов: код + scope + версия.

Миграция запрещает update/delete для ledger Points, событий Trust, присвоений ранга, истории задания, решений проверки, истории Reward, сообщений и истории поддержки. Исправление выполняется компенсирующим событием.

## 14. Идемпотентность

Уникальный `idempotencyKey` обязателен для:

- оценки доступности;
- назначения задания;
- операции VX Points;
- изменения ранга;
- события Trust Score;
- создания VX Reward;
- уведомления.

Повтор команды с тем же ключом должен вернуть ранее созданный результат. Тот же ключ с другим payload должен считаться конфликтом. Точная транзакционная реализация остаётся следующей частью Stage 13.

## 15. Контракты

`lib/domain` содержит независимые DTO, money/version/idempotency boundaries и state machines. `lib/repositories/domain-repositories.ts` определяет чтение и append-операции. `lib/services/domain-services.ts` определяет будущие use-case контракты.

Контракты используют `userId` и actor context. Они не принимают от клиента роль, рынок или owner как основание разрешения. Pagination является cursor-based; сортировка и фильтры должны проходить allowlist будущего сервиса.

## 16. Источники истины

| Данные | Канонический источник после интеграции |
|---|---|
| Вход и сессия | `User`, `Session` |
| Роль, рынок, язык, контакт, доступ | `UserProfile` и ролевой профиль |
| Согласие | `ConsentVersion` + `UserConsent` |
| Доступность возможности | `OpportunityAudience` + последняя допустимая `OpportunityEligibility` |
| Условия задания | Принятая `TaskVersion` |
| Результат | Конкретная `SubmissionVersion` |
| Решение | `SubmissionReview` |
| VX Points | Сумма подтверждённых ledger entries |
| Ранг | Последнее допустимое событие `UserRank` |
| Trust Score | `TrustScoreEvent`; snapshot только ускоряет чтение |
| Reward | `VXReward` + `RewardStatusHistory` |
| Поддержка | Conversation, messages и status history |
| Прогноз | Опубликованная версия + серверное access rule |
| Критические действия | `AuditEvent` |

## 17. Development seed

Production seed не создан. Для будущей локальной среды допустим отдельный, явно development-only seed с двумя рынками, пятью определениями рангов без порогов, тестовыми инфраструктурными ролями и сущностями, помеченными как synthetic. Он не должен содержать реальные контакты, суммы, промокоды, партнёров или пользовательские достижения.

## 18. Что пока не реализовано

- repositories и services не имеют Prisma-реализации для продуктовых моделей;
- нет API, Server Actions и frontend-интеграции;
- нет транзакционной бизнес-логики переходов;
- нет реальных начислений, проверок, Rewards, поддержки и прогнозов;
- миграция не применялась к production или неизвестной базе;
- mock/demo/localStorage остаются на месте до отдельной миграции;
- не утверждены значения экономики, сроки, валюты, юридические тексты и production data-retention rules.
