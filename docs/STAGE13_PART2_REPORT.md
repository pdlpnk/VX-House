# Отчёт по Этапу 13, часть 2 — фундамент аутентификации

## Результат

Подготовлен полноценный серверный фундамент аутентификации без подключения к существующим страницам, Dashboard, Landing или onboarding. Система готова к будущему использованию в route handlers и server actions, но сейчас не меняет поведение ни одного пользовательского маршрута.

## Что реализовано

### Архитектура аутентификации

Серверный контур разделён на независимые слои:

- криптографические примитивы, cookie и guards в `lib/auth`;
- контракт и Prisma-реализация auth repository в `lib/repositories`;
- жизненный цикл аутентификации в `lib/services`;
- сборка зависимостей в `lib/server`;
- параметры сессий в общей проверяемой конфигурации.

Зависимости передаются явно. Сервис аутентификации не связан с UI и не доверяет роли, переданной клиентом.

### Password hashing

Для паролей выбран PBKDF2-HMAC-SHA-256 через стандартный Web Crypto API:

- 600 000 итераций;
- уникальная случайная соль длиной 128 бит;
- хеш длиной 256 бит;
- версионированный формат хранения с параметрами алгоритма;
- проверка в постоянное время для значений одинаковой длины;
- фиктивное полное вычисление при отсутствующем или некорректном хеше, чтобы уменьшить различие времени ответа для неизвестного пользователя;
- ограничение допустимого размера пароля и параметров сохранённого хеша.

Решение соответствует актуальной минимальной конфигурации OWASP для PBKDF2-HMAC-SHA-256 и не зависит от нативных бинарников. Это важно для совместимости Node и текущего Cloudflare runtime. Формат допускает последующую миграцию алгоритма без изменения контракта сервиса.

### Session management

Реализован серверный жизненный цикл:

- `login` — единая нейтральная ошибка для неизвестного пользователя, неверного пароля и отключённого аккаунта;
- `authenticate` — проверка токена, отзыва, idle-expiration, absolute-expiration и состояния пользователя;
- `refresh` — атомарная ротация токена и продление только в пределах абсолютного срока;
- `logout` — отзыв текущей сессии и очистка cookie;
- `logoutEverywhere` — инфраструктурная возможность отозвать все сессии пользователя.

Токен сессии содержит 256 бит криптографической случайности. В базе хранится только HMAC-SHA-256 отпечаток токена, связанный с серверным секретом. Исходный токен существует только в cookie. Ротация использует условное обновление записи, поэтому повторное использование старого токена после успешного refresh не проходит.

Стартовые сроки являются серверной конфигурацией:

- idle-expiration — 7 дней;
- absolute-expiration — 30 дней;
- рекомендация refresh — после 24 часов.

Это стартовые инфраструктурные значения, а не продуктовые правила.

### Безопасная cookie-аутентификация

Cookie формируется со следующими свойствами:

- `HttpOnly`;
- `SameSite=Lax`;
- `Path=/`;
- `Secure` в production;
- префикс `__Host-` в production;
- отсутствие `Domain`;
- ограниченный `Max-Age`;
- явная очистка через истёкший cookie.

Для state-changing запросов подготовлена отдельная проверка `Origin`. Она не подключена к страницам или API, потому что соответствующие endpoints в этой части не создавались.

### Repository и Prisma

Инфраструктурная схема дополнена:

- версионированным password hash пользователя;
- датой изменения пароля;
- idle и absolute сроками сессии;
- датами refresh, последнего использования и отзыва;
- индексами сроков сессии.

Создан Prisma repository, который загружает роли и разрешения только из базы, создаёт, находит, ротирует и отзывает сессии. Добавлена начальная SQL-миграция инфраструктурных моделей. Миграция не применялась к реальной базе.

### Guards и server middleware

Подготовлены три политики серверного доступа:

- `public`;
- `authenticated`;
- `role`.

Role-based policy принимает только инфраструктурные ключи ролей, полученные сервером из базы. Роли игрока, партнёра и другие бизнес-роли не зашивались.

Middleware возвращает `401` при отсутствии действующей сессии и `403` при недостатке серверных прав. Guards доступны отдельно для route handlers и server actions. Корневой middleware и существующие маршруты не изменялись.

## Выбранные решения

1. **Stateful opaque sessions вместо JWT.** Сервер может немедленно отозвать сессию, ограничить абсолютный срок и безопасно ротировать токен.
2. **Только HMAC-отпечаток в базе.** Утечка таблицы сессий не раскрывает действующие bearer-токены.
3. **PBKDF2 через Web Crypto.** Выбран переносимый, стандартизованный и поддерживаемый runtime алгоритм без нативных модулей.
4. **Два срока жизни.** Idle-expiration ограничивает неактивную сессию, absolute-expiration исключает бесконечное продление.
5. **Server-side RBAC foundation.** Клиентские значения ролей не участвуют в решении о доступе.
6. **Dependency injection.** Repository, token manager и cookie manager можно тестировать и заменять без переписывания интерфейса сервиса.
