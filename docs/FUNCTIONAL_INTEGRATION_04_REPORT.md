# Functional Integration Module 4 — Support + Appeals + Notifications

## Статус

Модуль завершён. Локальные демонстрационные обращения, сообщения и пустой notification popover заменены серверными данными PostgreSQL через Prisma.

Forecasts, Promocodes и административные бизнес-операции не реализовывались.

## Что стало работать

### Support Conversations

- серверный каталог категорий с фильтрацией по роли и рынку;
- создание обращения с категорией, приоритетом, темой и первым сообщением;
- список и карточка только собственных обращений;
- реальный статус и append-only история переходов;
- серверный timestamp для обращений, сообщений и истории;
- отправка новых сообщений в существующий диалог;
- автоматический переход `WAITING_USER/RESOLVED → WAITING_OPERATOR` после ответа пользователя;
- шифрование текста сообщений AES-256-GCM перед сохранением;
- идемпотентность создания обращения и отправки сообщения;
- rate limiting и same-origin-защита командных маршрутов;
- честное отсутствие вложений: файловая отправка не реализована.

### Appeals

- создание апелляции по отклонённому заданию или допустимому статусу VX Reward;
- серверная проверка ownership и текущего статуса связанной сущности;
- запрет двух активных апелляций по одному основанию;
- связь апелляции с обращением поддержки;
- атомарное создание обращения и апелляции из контекстной ссылки задания/Reward;
- lifecycle `DRAFT → SUBMITTED → UNDER_REVIEW → решение` через server state machine;
- append-only `AppealStatusHistory`;
- запрет изменения причины и источника после отправки.

### Notifications

- реальные IN_APP-уведомления из серверного источника;
- категории через тип события;
- состояния `SENT` и `READ` с серверным временем;
- append-only история статусов;
- unread count и список в существующем popover Dashboard;
- идемпотентная отметка owned-уведомления прочитанным;
- создание уведомлений доступно только внутреннему сервису с permission `notifications.write`.

## Серверные контракты

- `GET /api/support`;
- `POST /api/support`;
- `GET /api/support/:id`;
- `POST /api/support/:id/messages`;
- `POST /api/appeals`;
- `GET /api/notifications`;
- `POST /api/notifications/:id/read`.

Операторские переходы статусов, решения апелляций и создание уведомлений не опубликованы как пользовательские API. Они подготовлены как защищённые внутренние команды с permissions `support.write`, `appeals.write` и `notifications.write`.

## Какие demo-данные удалены

- удалены четыре фиктивных обращения из `lib/support-data.ts`;
- удалены фиктивные сообщения пользователя и оператора;
- удалены локальные функции `getSupportTickets` и `getSupportTicket`;
- Support Center больше не показывает «демонстрационный список»;
- форма создания обращения включена и пишет реальные серверные данные;
- composer отправляет реальные append-only сообщения;
- пустой notification popover заменён серверным списком unread/read;
- локально остались только русские presentation-labels статусов и приоритетов.

## Безопасность и целостность

- ownership применяется к каждому чтению и пользовательской команде;
- роль и рынок берутся только из подтверждённого серверного профиля;
- недоступная категория не создаёт частичных данных;
- сообщения шифруются и не возвращают внутренние заметки;
- update/delete сообщений, историй поддержки, апелляций и уведомлений запрещены DB triggers;
- закрытый диалог не принимает новые сообщения;
- клиент не назначает оператора и не меняет status;
- клиент не создаёт уведомления и не принимает решение по апелляции;
- вложения сознательно не реализованы.

## Найденные и устранённые проблемы

- `Appeal` не имел прямой связи с `UserTask`; добавлена ownership-проверяемая связь;
- у Appeal и Notification не было отдельной истории статусов; добавлены append-only журналы;
- категория обращения была произвольной строкой; добавлен серверный каталог с role/market-фильтрацией;
- существующий DB invariant создавал обращение с несуществующей категорией; fixture обновлён на реальный FK-контракт;
- UI показывал вымышленные ответы оператора; они удалены без переноса в seed;
- тексты сообщений могли храниться как обычный JSON; новый сервис использует защищённое AES-GCM хранение;
- создание обращения и апелляции через два независимых запроса создало бы риск частичного результата; операция объединена в одну транзакцию.
