# Functional Integration Module 3 — Economy + VX Rewards

## Статус

Модуль завершён. VX Points, Trust Score, ранги и VX Rewards переведены с локальных демонстрационных данных на серверные read/command-модели PostgreSQL через Prisma.

Support, Forecasts и административные бизнес-операции не реализовывались.

## Что стало работать

- append-only ledger VX Points с подтверждёнными, ожидающими и корректирующими записями;
- серверный баланс: клиент не передаёт и не вычисляет итог;
- идемпотентное применение версионированных правил Points и Trust;
- Trust Score с неизменяемыми событиями, snapshot, диапазоном 0–100, зоной и объяснимой причиной;
- серверный расчёт текущего и следующего ранга по опубликованным критериям роли и рынка;
- append-only история повышения ранга без автоматического понижения;
- каталог назначенных пользователю VX Rewards;
- карточка Reward с типом, значением, основанием, сроком, доступностью и историей;
- серверный lifecycle Reward и идемпотентный claim;
- объединённая история Points, Trust, Rank и Reward;
- реальные показатели экономики на главной кабинета игрока и партнёра;
- честные пустые состояния при отсутствии конфигурации, событий или Rewards.

## Серверные контракты

- `GET /api/economy`;
- `GET /api/economy/history`;
- `GET /api/rewards`;
- `GET /api/rewards/:id`;
- `POST /api/rewards/:id/claim`.

Публичных маршрутов для изменения баланса, Trust Score или ранга нет. Экономические команды доступны только внутреннему серверному сервису с инфраструктурным permission `economy.write`. Role, market, ownership, eligibility Reward и допустимость перехода проверяются сервером.

## Архитектурные решения

- `EconomyPolicy` хранит версионированные правила Points, Trust, стартовый Trust и зоны для scope роли/рынка. Опубликованная версия неизменяема.
- `PrismaEconomyRewardRepository` является единым persistence-слоем модуля.
- `EconomyRewardApplicationService` собирает read model и выполняет транзакционные команды.
- Balance вычисляется суммой `CONFIRMED` и отдельных `REVERSED` записей ledger; `PENDING` показывается отдельно.
- Коррекция Points создаёт новую отрицательную запись со ссылкой на исходную; update/delete ledger запрещены DB trigger.
- Trust Score изменяется только правилом активной `EconomyPolicy`; snapshot всегда ссылается на последнее событие.
- Rank определяется по наиболее специфичной опубликованной версии критериев и повышается только при выполнении всех условий.
- `RewardStatusHistory` фиксирует каждый переход; недопустимые переходы отклоняет общая state machine.
- Экономические команды выполняются в serializable-транзакциях; ошибка любого правила откатывает command целиком.
- Идемпотентные replay возвращают тот же результат, а повторное использование ключа с другим payload отклоняется.

## Какие demo-данные удалены

- удалён `lib/economy-data.ts`;
- удалён `lib/reward-data.ts`;
- удалены локальные `null`-snapshot экономики, demo reward types и reward previews;
- удалён интерактивный frontend-переключатель фиктивных статусов Reward;
- Dashboard больше не показывает зашитые заглушки вместо Points, Trust и ранга;
- Economy и Rewards UI получают данные только из server service.

Статические русские подписи и объяснения сущностей остаются presentation-копирайтом и не участвуют в расчётах.

## Безопасность и целостность

- клиент не передаёт balance, rank или trust;
- чтение Reward и claim ограничены владельцем;
- роль и рынок берутся из подтверждённого серверного профиля;
- приостановленный/закрытый профиль не получает доступ к экономике;
- published policy и критические истории защищены от изменения;
- monetary Reward требует сумму и валюту, non-monetary Reward — точное описание значения;
- expired, неготовый и уже предоставленный Reward нельзя получить повторно;
- команды Points, Trust, Rank и выпуска Reward не опубликованы как пользовательские API.

## Тесты

Изолированный PostgreSQL-набор: **45 из 45 успешно**, включая 7 новых end-to-end integration-сценариев модуля:

- ledger и серверный баланс;
- идемпотентное применение правил;
- Trust Score, зона и история;
- rank promotion и история;
- компенсирующая запись Points и append-only защита;
- Reward lifecycle и идемпотентный claim;
- ownership и availability;
- объединённая история;
- транзакционный rollback при ошибке второго правила.

Также успешно:

- Prisma validate;
- Prisma generate;
- domain tests: 4 из 4;
- production build;
- typecheck;
- lint;
- статические/SSR-контракты: 12 успешно, 6 защищённых SSR-сценариев ожидаемо пропущены без fixture-сессии.

Desktop/mobile smoke выполнен на локальном production-сервере: `/` и `/access` вернули HTTP 200 для desktop и mobile User-Agent. Структура защищённых страниц не менялась, используются прежние responsive grid/layout и `prefers-reduced-motion`; их экономические read models и команды дополнительно проверены с реальной изолированной БД и серверной principal-сессией.

## Найденные и устранённые проблемы

- общий запуск нескольких DB test-файлов создавал конкуренцию транзакций одной stateless-базы; runner переведён на последовательный запуск файлов;
- старые статические тесты зависели от удалённых demo-модулей; контракты обновлены на server-backed архитектуру;
- Reward transition replay искал запись по actor вместо владельца; replay теперь восстанавливает owner на сервере;
- производные idempotency keys могли превысить лимит поля; они заменены на стабильные SHA-256 ключи;
- snapshot внутри транзакции обращался к root Prisma client; все чтения переведены на transaction-scoped repository.

- реальные операционные процессы предоставления денежных и неденежных Rewards;
